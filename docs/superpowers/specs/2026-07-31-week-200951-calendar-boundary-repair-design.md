# week_id=200951 权威日历边界修复设计

**日期**：2026-07-31

**状态**：IMPLEMENTED

## 目标

解决 `weekly_10y_d_overlay_0529` 历史复现因 `week_id=200951` 无法取得最后
交易日而 fail-closed 的问题。修复权威数据库日历覆盖，不修改算法核心、不使用
ISO 周日期兜底，也不降低 2025 年以后回测和实时路径的日历门禁。

## 已确认根因

平台日历语义由两张数据库源表共同提供：

- `api_wind_date` 提供 `rdate -> week_id`；
- `t_trade_calendar` 提供 `rdate -> trade_flag`。

当前 `api_wind_date` 最早包含
`2009-12-31 -> week_id=200951`，但 `t_trade_calendar` 从
`2010-01-01` 才开始。`2010-01-01` 至 `2010-01-03` 均为非交易日，因此
两表 JOIN 后，`week_id=200951` 没有任何 `trade_flag=1` 的日期。

上游日期代码
`/Users/macstudio0/bondprojectpro/BondPrediction/insertDateList.py`
通过同目录 `cn_stock_calendar.py` 生成权威交易周。对
`2009-12-28` 至 `2009-12-31` 运行该规则，四天均为交易日且都属于
`week_id=200951`。问题来自日历覆盖起点，不是 D-overlay 算法逻辑。

## 选定方案

由上游日期生产链生成 `2009-12-28` 至 `2009-12-31` 的四条权威日历记录，
在单一数据库事务中幂等补齐：

1. `api_wind_date(rdate, week_id)`；
2. `t_trade_calendar(id, rdate, trade_flag, week_id, week_name)`。

写入前必须逐行核对生成结果；仅允许四个明确日期，且每行必须满足：

```text
week_id = 200951
trade_flag = 1
```

写入不得删除或批量重算任何已有日期，不得扩展到整个 2009 年。若已有行与预期
冲突，停止而不是覆盖；若已有行完全一致，则按幂等 no-op 处理。

`bond-factor-lab` 继续只读这两张源表，不增加源表写库代码。

## 被否决方案

### 平台适配器回退到 ISO 周五

该方案会在数据库日历缺失时产生第二套日期真值，掩盖数据源问题，并可能把权威
交易周编号误解为 ISO 周编号，因此不采用。

### 删除 2009 年预热数据

预热数据参与模型训练、滞后和差分特征构造，删除可能改变算法输出，不符合源算法
保真要求。

### 补齐整个 2009 年日历

当前失败仅涉及跨年周 `200951`，整年回填扩大写入面，并可能触碰旧周频数据的
历史编号口径；不符合最小修复原则。

## 操作与失败边界

操作分为四段：

1. 只读 precheck：核对两表现状及四条预期记录；
2. 单事务 apply：只插入缺失且无冲突的四个日期；
3. 只读 postcheck：确认 `CalendarService` 将 `200951` 映射到
   `2009-12-31`；
4. 平台诊断：运行
   `python -m backtests.weekly_10y_d_overlay_0529_reproduction --no-persist`，
   将日历边界修复与当前输入 vintage/benchmark 漂移分开验收。

任一条件不满足时立即回滚：

- 生成结果不全属于 `200951`；
- 任一日期不是交易日；
- 现有数据库行与生成结果冲突；
- 写入范围超出四个日期；
- 修复后平台日期不是 `2009-12-31`。

本次不持久化新的回测 run，不修改或删除已有预测、实际值与历史回测数据。

## 验收标准

- `api_wind_date` 与 `t_trade_calendar` 对四个日期逐行一致；
- `week_id_to_last_trading_day(200951) == "2009-12-31"`；
- 当前 2025 年以后及实时周的权威日历映射不变；
- `weekly_10y_d_overlay_0529` 能越过 `200951` 日历解析并构造 72 行历史结果；
- 算法核心、配置和预测逻辑零改动；
- 问题台账明确区分：
  - `202625` 生产冲突已经修复并完成缺口回补；
  - `200951` 是独立的历史日历覆盖边界，完成本次修复后关闭；
  - 当前输入 vintage 与旧 benchmark 的差异另行建单并保持 fail-closed。

## 独立 benchmark 漂移

只读审计在内存模拟 `200951 -> 2009-12-31` 后确认，当前输入可以构造
72 行历史结果，但与旧 original benchmark 对比时，45 个 feature week 中有
14 个周存在内部字段差异，其中 `202538`、`202548`、`202602` 方向翻转。

该差异在日历修复前已经存在，不能作为回滚正确日历补数的条件，也不能通过修改
算法、benchmark 或置信度贴合。日历修复完成后，`--no-persist` 仍应保留原
CompareGate 并因该独立漂移 fail-closed；输入 vintage 问题必须单独研究和关闭，
之后才能重新声明当前 DB 输入下 `45/45`。

## 实施结果

2026-07-31 已按本设计完成单事务补数：

- `api_wind_date` 新增 3 行，既有 `2009-12-31` exact no-op；
- `t_trade_calendar` 新增 4 行；
- 两表目标日期均为 4 行/4 个唯一日期，全表重复日期组均为 0；
- `CalendarService` 映射 `200951 -> 2009-12-31`，且
  `202625 -> 2026-07-03` 未受影响；
- 只读模型验收成功构造 72 行、17 个月，随后按预期在独立 benchmark 漂移处
  fail-closed；
- 三份旧 Native generation 均保持 sealed 且未被原地改写；新日历制品产生新
  SHA/combined input identity，后续只能生成新 generation，不能覆盖旧证据。
