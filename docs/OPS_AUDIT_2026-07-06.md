## 已修复问题

### P1: Metrics 未按 registry horizon 隔离

根因：`backend.services.scheme_metrics()` 只按 `base_scheme_id + target_tenor` 过滤预测行，漏掉 `p.horizon = registry.horizon`。同一 base/tenor 若同时存在 h1/h5，会污染 composite registry ID 的前端统计。

修复：`scheme_metrics()` 增加 horizon 过滤；新增回归 `test_scheme_metrics_isolates_registry_horizon`。

### P1: 后端 admin token fail-open

根因：`BOND_ADMIN_TOKEN` 未配置时 `require_admin_token()` 直接放行，和部署文档“本地直连也必须携带 X-Admin-Token”的第二道闸冲突。

修复：未配置 token 时 admin/trigger 写接口返回 503；更新 `tests/test_backend_api.py`、`docs/CURRENT_STATUS.md`、`deploy/README.md`、backend launchd 模板和外部访问设计文档。GET 展示接口不受影响。

### P1: Actual 表可能保留源表已回滚的 tail stale rows

根因：`update_actuals()` 只 UPSERT，不清理晚于当前 `api_wind_daily` 水位的 actual。只读证据显示 `1Y/3Y/5Y/7Y` 的 `t_scheme_actuals.trade_date=2026-07-02` 在当前源表无对应 `rdate`。

修复：新增 `read_source_watermarks()` 和 `delete_actuals_after_source_watermark()`，刷新日频 actual 后只清理每个 tenor 晚于源表最大日期的 tail rows，并记录 warning。该修复不会删除中间历史缺口，避免上游短暂缺行导致误删历史验证。

### P1: StaticGate 未递归扫描真实公共 backtest runner

根因：config 指向薄 wrapper，StaticGate 只解析 wrapper 文件；wrapper 再 import 公共 runner 时，公共 runner 的 scheduler live 边界依赖逃过检查。

修复：StaticGate 递归扫描 `backtests.*` 本地依赖，并显式覆盖 `from backtests import shared_runner`、`from . import shared_runner`、`from .shared_runner import run` 等 package alias / relative import；新增 transitive import、package alias import 与 relative import 回归。将 0629 日度/月度公共 runner 从 `scheduler.repository` / `scheduler.*_actuals_updater` 依赖剥离到 `backtests.repository` / 新增 `backtests.actuals`。

### P1: ActivationGate 可把 skipped CompareGate 当作通过

根因：`_verify_gate_history()` 对所有 gate 状态把 `passed/skipped` 都计入完成。对 `benchmark_required=true` 的 source-backed 方案，CompareGate skipped 表示对比没有发生，不应激活。

修复：若 config `backtest.benchmark_required=true` 且 compare 状态为 skipped，ActivationGate 阻断；新增 SQLite gate history 回归。

### P2: CompareGate 忽略 row-level benchmark_role

根因：strict fields/key fields 不含 `benchmark_role`，source-original 与 source-compatible/live-safe 行可能被混作同一主键。

修复：strict schema/key 加入 `benchmark_role`；周频/月频 strict key 同步纳入 role；更新 SOP/PREDICTION_SEMANTICS 文档。

复查补修：`benchmark_role` 是“逐样本可比口径”，不是 original/current 文件来源。已有 summary provenance 已表达 source/platform 来源。因此本轮同步迁移 36 个 tracked benchmark CSV：旧历史样本补 `benchmark_role=historical/source-original`，已有 role 但 current/original 不一致的样本按相同业务 key 将 current role 对齐到 original role。迁移后 `t1_daily` 和 `weekly_avg_1y_lgbm_0529` CompareGate 均通过，且全仓 benchmark CSV 检查显示缺 role/空 role/两侧 role 不一致均为 0。

复查补修后新增 `test_tracked_benchmark_samples_have_nonempty_aligned_roles`，把全仓 tracked benchmark CSV role 审计纳入单测，避免该保证只依赖一次性脚本。

### P2: benchmark_required config 未强制声明 benchmark identity

根因：`validate_config()` 未要求 `backtest.benchmark_id` / `backtest.data_source`。`t1_daily` 与 `t5_daily` active config 缺这两个字段。

修复：schema 在 `benchmark_required=true` 时强制要求 identity；补齐 t1/t5 config 为 `model_muti_0529` / `framework_db_aligned`。

### P2: 周历 fallback 可返回非交易日

根因：`CalendarService.week_id_to_last_trading_day()` 在缺少 `_week_last_trading_day` 时 fallback 到 `api_wind_date MAX(rdate)`，未 join `t_trade_calendar.trade_flag='1'`。

修复：fallback 也必须 join 交易日历；无交易日则 fail-closed 抛错。新增“不能 fallback 到周末”的回归。

### P2/P3: scheduler actuals 和 executor 运维风险

修复项：
- `run_actuals_job()` 已保留 monthly actuals 在非交易日刷新；2026-07-11 追加修复后，非交易日 daily/weekly actuals 不再完全跳过，而是刷新到上一交易日，避免周五源数据晚于 `23:45` 才补入时 T+1 最新验证卡到周末。

- `execute_scheme()` 新增 daily live 日期语义校验：`predict_date` 必须等于本次 run，`feature_date` 必须等于 `previous_trading_day(predict_date)`，`target_date` 必须等于 `feature_date + horizon` 个交易日；若算法因源水位不足复用旧 feature/target，统一 fail-closed 且不写 prediction。

2026-07-09 后续处置：scheduler launchd 配置已同步为 `RunAtLoad=true`、`KeepAlive=true`，并显式设置 `BOND_SCHEDULER_STARTUP_CATCHUP=1`。`scheduler.main` 启动后会补跑当天业务 cron 已过且 `t_scheme_runs` 没有 `success/partial/failed/skipped` 终态记录的 active 任务；已有终态 run 会跳过，避免重启重复写库。actual 刷新窗口从 `08:30/19:00` 增加为 `08:30/19:00/23:45`，夜间档承接上游 BondPrediction `23:25` 左右的 Wind 日频导入。

### P2: 健康检查未覆盖 run/prediction 归属与 stale live 语义

根因：此前只看 `predict_date` 总行数和 active scheme 成功 run，无法发现“run log 成功但预测明细被后续 run 覆盖”的情况，也无法发现“当天 run 成功但记录复用旧 feature_date/target_date”的 stale live 行。

修复：`scripts/check_production_daily_health.py` 增加两类 error：
- `successful_run_prediction_rows_mismatch`：成功 run 的 `records_written` 与按 `run_id` 统计的 prediction rows 不一致。
- `daily_prediction_date_semantics_mismatch`：active 日频 prediction 的 `predict_date/feature_date/target_date` 与平台日历语义不一致。

同时补充已知日频方案输入水位知识表；当某交易日所有 active 日频方案都因源表水位早于 expected feature date 而无有效预测时，将 `daily_predictions_missing` 降级为 warning，并在 `daily_run_input_watermark_blocked` 中列出阻塞期限，避免诱导人工伪造预测。

## 可维护性防线

- 新增只读脚本 `scripts/check_production_daily_health.py`，用于日常巡检交易日日频预测是否整体缺失、active 日频 base scheme 是否有成功 run、`t_scheme_actuals` 是否晚于源表水位，并对已知日频方案族输出缺 run 对应的 source watermark 阻塞期限。
- 默认把“部分 active 方案没有成功 run”标为 warning，避免 source-backed 方案 fail-closed 时诱导人工补写；加 `--strict-runs` 可在验收窗口把该项升级为 error。
- 脚本会检查 successful run 的 `records_written` 是否能按 `run_id` 对上 prediction 明细，并检查 active 日频 prediction 是否符合 live 日期语义。这样可以在前端出现异常前发现 stale live 覆盖旧 target 的问题。
- executor 层已经统一阻断 stale daily live 输出；如果上游源数据没有覆盖 expected feature date，方案必须 fail-closed，不得复用上一交易日预测或人工补写。
- 建议 scheduler 运行日 08:00 后、actuals 刷新后各跑一次该脚本，并把非 0 退出码接入告警通道：`0=ok`，`1=warning`，`2=error`。
