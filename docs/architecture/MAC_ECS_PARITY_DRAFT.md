## 1. 目标

**在不改变现有方案业务逻辑的前提下，让同一份输入数据在 Mac 和 ECS 上，经过同一套调度、数据桥、runner 和算法，产出完全相同的最终预测数值与方向；验证通过后，把控制固化进生产算法，只影响后续预测，不回填历史、不重跑回测。**

### 1.1 四个“一致”

| 一致 | 操作化定义 |
|---|---|
| 数据一致 | 算法读取那一刻实际消费的每个值相同（不是文件 SHA 相同） |
| 算法一致 | 脚本 SHA + 配置 SHA + 环境清单 SHA 相同，执行控制相同 |
| 预测一致 | 同一业务键，最终判定标量在容差内，方向完全相同 |
| 后续预测一致 | 切换后，两端在线预测持续满足上一行 |

### 1.2 验收轴

- **只比两端，不比新旧。** 数据已经变化，历史输出不可复现，也不要求复现。
- 历史预测与历史回测是账本，冻结；本次变更只影响后续预测。
- 参照物是“同一份输入数据”，不是 Mac 的历史预测。验收上两端对等；只有出现无法消除的差异时，才指定一端为规范端。
- 验收对象是预测数值与方向，不是回测绩效指标（actuals 两端可能不同，指标一致不能由预测一致推出）。

### 1.3 范围（2026-10-24）

注册表 110 套方案（多期限方案按期限分别计数）= **两端共有 101 套** + W4 原生 9 套（仅 Mac，不迁移、不参与比对）。

- **Phase 1**：21 个已知不一致方案（2026-10-20 定），2026-10-21 闭环，台账见第 13 节。
- **Phase 2**：其余 80 个共有方案，2026-10-24 完成，结果见第 12 节。
- **迁移本身**（阶段 E：ECS 成为唯一数据源头与生产写入方，Mac 改为只读算力与验证平台）暂缓，待用户确认阶段 D 后启动。

## 2. 第一性原理

1. **预测是函数**：`输出 = 算法(算法实际读到的输入)`。两端输出不同，只可能来自输入不同或执行不同。
2. **输入不是文件，是读取那一刻实际消费的值。** 输入链为：调度 → 数据桥 → runner → 算法。
3. **顺序必须先上游、后下游。** 先证明输入边界一致，再证明算法内部一致；上游没对齐，下游对照无法归因。
4. **算法逻辑不动，动的是未约定的执行控制**：排序、采样、解析、滚动、线程、精度、初态。
5. **内部细节是手段，不是验收对象。** 验收只看最终数值和方向；深入内部是为了定位分歧点、证明固化有效、排除“碰巧一致”。
6. **一致性必须可证伪**：重复运行稳定、解除控制能复现差异、全量对照无反例。
7. **不接受笼统的“环境差异”作为结论。** 每一项差异都要落到具体机制、具体代码点。只有证明确属 CPU 架构（Mac arm64 vs ECS x86_64 数值库）、无法用确定性控制消除且方向一致的末位差异，才按 6.3 登记后允许上线；原因不明的继续排查。
8. **不为对齐而调参。** 不新增 epsilon、不改业务阈值、不换模型或采样分支。

## 3. 判据与术语

### 3.1 三个门槛，必须同时成立

| 门槛 | 判据 | 容差 |
|---|---|---|
| **结构一致** | 选中的列、排序顺序、抽样序列、树结构、票数成员完全相同 | 0（精确） |
| **数值一致** | 最终判定标量差值 ≤ τ | τ，见第 6 节 |
| **方向一致** | `predicted_direction` 完全相同 | 0（精确） |

结构差异是失败，不能用容差盖过去。方向不一致是失败，无论数值多接近。

### 3.2 最终判定标量

不是笼统的“概率”，而是每个方案实际用于产生方向的最后一个数值（如 T5 模板的 `ens_prob` / 投票分数、factor/ensemble 的 `combined_score`、weekly logit 的 `predict_proba`）。Phase 2 同输入探针按“最终概率 + 全部中间值”的 `float.hex` 逐位比对。

> **契约缺口（未决，见第 10 节 O4）**：Blackbox V2 交付契约的 `RESULT_FIELDS` 只包含 `predicted_direction`，概率/分数是内部值，由探针/观察器采集。

### 3.3 “同一份数据”

指算法读取那一刻实际消费的值相同，至少包括：

- 解析后的源路径、SHA、大小、行数、列序、dtype、NA 掩码；
- 实际消费列的逐元素 IEEE 位；
- daily / weekly / monthly cutoff 键及其解析到的数据 vintage；
- 业务键（predict_date / feature_date / target_date）、运行时刻、时区、交易日历；
- 环境变量、cwd、参数、runner/数据桥版本。

日常运行中以 DataBridge 发布为准判定输入一致（见 11.1）。

## 4. 输入链与四层边界

```
调度（哪个业务键、什么时刻、哪个 cutoff、哪个 vintage）
  → 数据桥（选哪些文件/行/列，行序、dtype、NA、派生表）
    → runner（解释器、环境、cwd、参数、路径、缓存、并发）
      → 算法（特征、评分、排序、采样、训练、融合、历史规则）
        → 最终数值与方向
```

| 层 | 可能造成的差异 | “一致”的判据 |
|---|---|---|
| 调度 | 同一业务键在不同时刻运行；cutoff 落在不同 vintage；时区/日历不同 | 业务键、运行语义、cutoff 解析结果相同 |
| 数据桥 | 选到不同文件/行/列；行序、dtype、NA 处理不同；缺失回退不同；派生表不同 | 算法消费的每个值相同 |
| runner | 解释器/环境变量/cwd/参数/路径不同；缓存或临时目录不同；并发/超时导致部分执行 | 同脚本、同环境清单、同参数、同路径语义、同初态 |
| 算法 | 排序、采样、解析、滚动、训练、融合、规则 | 内部决策点逐层可解释，最终数值一致 |

**调查范围覆盖四层；改动范围取决于结论。** 如果差异来自调度、数据桥或 runner，它们也必须纳入控制或修复，不能只改算法。数据问题在入库层解决，不在模型侧补偿。

## 6. 容差规范

### 6.1 定义（已采用）

对每个方案的最终判定标量：

```
τ = 10 × Δ_max；Δ_max = 0 时 τ = 0（精确相等）
```

- **Δ_max**：控制全部固化后，同一输入下双端最终判定标量的最大实测残差。
- **前提**：τ 必须远小于 **M_min**——全量日期（含历史上下文日期）到**任何**离散判定边界的最小距离；边界包括当前阈值、加权融合阈值、历史票数边界、override 规则。Phase 2 登记的架构末位差为 1e-16 量级，与判断阈值的距离相差 10^5 倍以上。
- 若 10 × Δ_max 接近 M_min，不存在安全的统一容差：不设 τ，逐日核对方向（`weekly_10y_d_overlay_0529` 即此情形）。

### 6.2 为什么容差必须分方案、分标量

- float32 方案在 1e-12 下永远不可能通过，表示精度本身就在 1e-7；
- float64 方案用 1e-6 又太松，可能掩盖真实的结构性差异；
- 容差必须跟随标量的 dtype 和它到决策边界的距离。

### 6.4 决策边界安全（含历史传播）

O022 已证明：历史投票差 1 票（10 → 11）越过严格 `>10`，最终方向翻转。因此：

- τ 必须小于当前阈值的安全距离；
- 还必须小于**历史上下文每一天**到其判定边界的距离；
- 否则即使今天分数一致，历史票也可能因为另一天落在容差带内而翻向。

## 11. 运行规则与验证方法

### 11.1 输入一致

- 两端输入一致以 **DataBridge 五文件 SHA256 与 publication manifest `business_digest`** 为准，不以原始表全表哈希为准；不进入 DataBridge 的原始行差异（如爬虫实时行情）忽略。
- 每日门禁：两端 `business_digest` 相等。不等时按全局目标文档决策 10 在入库层定位修复，不在模型侧补偿。
- DataBridge 源表（`shared/data_contract.py`）：`api_wind_daily`、`api_wind_derivative_daily`、`api_wind_weekly`、`api_wind_derivative_weekly`、`api_wind_monthly`、`api_wind_derivative_monthly`、`api_wind_indicators_all`、`api_wind_date`、`t_trade_calendar`。
- 跨机数据覆盖只能一次性、manifest 绑定、经授权，只覆盖上述 9 张源表，不覆盖业务表（预测/回测/registry/versions/harness/runs）；actuals 不跨机覆盖，由各端 actuals 服务从源表重算。
- 覆盖方法（2026-10-22 实践）：改前 ECS 备份（dump + SHA256 + 行数 + 恢复脚本）；Mac `mysqldump --single-transaction` 只读导出；装载到 `<table>__stg`，一条 `RENAME TABLE` 同时切换；核对用按主键排序的全表文本 SHA256（ECS MySQL 8.4 的 `CHECKSUM TABLE` 对 InnoDB 返回 NULL，不能用）。

### 11.2 版本与激活

- 两端运行同一份不可变 release，不得现场改源码；只钉方案文件 SHA 不够，平台代码（`shared.input_artifacts`、runner、adapter）随 release 一起钉住。
- 确定性控制写入交付文件，产生新 exact，经 revision 激活：`business_tables_written=false`，旧 exact retired，历史预测不改不回填，新 exact 从下一次调度起生效。
- 激活准入（Phase 1 四道门）：交付可信（`.py`/`.json` 可执行、exact 可信）；已有 prior active exact（initial 激活会写历史产品事实，不做）；全量双端方向 0 不一致、数值 ≤ τ；只改排序/采样/解析/线程/列序等确定性控制。不满足则跳过并记录。
- `gray_target_start` 规则：`max(最后一条 live 预测日 + 1 交易日, 今天)`。
- 不自动加入 `production_schemes.json`。回滚边界：激活失败保持 paused；必要时回退 current 到 previous release。
- 已知阻断：交付目录只能有 `.py`/`.json` 两个普通文件（残留 `__pycache__/` 会让 `discover_schemes` 报错）；revision preflight 只接受 `blackbox_v2` 或已 retired 的 native 版本，遗留 paused `native_adapter` 版本须先备份再置 retired。

### 11.3 验证方法

- **同输入探针**：两端用同一份数据、走生产同一条路径计算，逐位比对最终概率与全部中间值（`float.hex`）；ECS 一轮约 20 分钟。比较存储的全精度值，不比格式化字符串；失败/超时/资源围栏单独记账，不从统计中静默剔除。
- **首分歧层定位**：trace 探针逐层比对（解析后输入 → 方案消费值 → 筛选分数 → 选列 → 拟合 → 概率 → 方向），再以“解除控制 → 差异复现”反证。例：`five_y_t5_xgb_spr_3y1y_b8_v1` 解析后全列哈希不同但消费值逐位相同，`screen_scores` 相同而 `selected` 8/8 天不同 → 定位到同分排序。
- **增量方案**：两端缓存数组逐元素比对 + 回测方向逐日一致。
- **回测路径 ≠ 在线路径**：探针/回测通过后，以实盘同业务键逐字段对照为最终验收。
- 验证量与改动成比例；只改平台代码（exact 不变）不需要回测（全局目标文档决策 8）。耗时任务先跑探针再跑全量。
