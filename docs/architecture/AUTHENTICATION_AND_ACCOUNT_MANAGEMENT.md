# 登录与账户管理设计

**文档状态**：`CURRENT`

**最后更新日期**：2026-09-03

**实施状态**：需求与实施顺序已确认；第一阶段以阿里云 ECS `aliyun-gray` 的 localhost 前端为实现与集成验收
目标，ECS 验收通过前不得晋级 Mac3

本文定义 Bond Factor Lab 独立登录、会话、账户与管理员用户管理的目标设计。系统不依赖、嵌入或复用其它
前端系统的身份能力；第一阶段只在 ECS 的独立 `bond_db` 验证。Mac3 暂不实施，未来晋级时仍使用自己的
`bond_db`，不复制、同步或共享账户数据。

## 1. 已确认需求

1. Bond Factor Lab 是完全独立的前后端系统，认证能力由本项目自身提供。
2. 账户数据存储在各环境现有的 MySQL 8.0 `bond_db` 中，不新建第二个 database。
3. 角色只分为 `admin`（管理员）和 `user`（普通用户）。
4. 用户删除采用停用/软删除；账户、审计和历史关系不做物理删除。
5. 页面右上角展示用户名。点击后只显示：
   - 个人资料
   - 修改密码
   - 退出登录
6. 管理员拥有独立的“用户管理”板块，可以创建用户、维护可选的用户姓名和机构名称、调整角色、重置密码、停用用户和恢复用户。
7. 管理员是网站账户管理员，不因此获得算法激活、生产预测写入、数据库迁移、补数、调度或服务控制权限。
8. 用户可以同时在多个浏览器登录；每次登录创建一条独立会话，所有会话均固定有效 12 小时。
9. 用户改密、管理员重置密码、改用户名、改角色或停用用户时，必须撤销该用户全部浏览器会话。
10. 恢复用户只恢复登录资格，不恢复任何已撤销或已过期的会话。

## 2. 第一阶段范围

### 2.1 包含

- 用户名和密码登录；
- 服务端可撤销会话；
- 登录、退出和当前用户查询；
- 用户修改自己的密码；
- 用户修改自己的可选姓名和机构名称；
- 管理员用户列表；
- 创建用户；
- 调整管理员/普通用户角色；
- 管理员重置用户密码；
- 停用和恢复用户；
- 管理员账户变更以及受保护管理员初始化/重置审计；
- Dashboard 与管理员 API 的后端权限保护；
- 初始管理员的一次性安全初始化和受控密码重置命令。

### 2.2 不包含

- 用户自行注册；
- 邮箱、手机号和短信验证码；
- 邮件找回密码；
- 第三方登录或 SSO；
- MFA；
- 部门、用户组、方案级权限或其它细粒度授权；
- session 与审计记录的自动归档或定时清理任务；
- Mac3 与 ECS 之间的账户同步；
- 页面控制算法、调度、迁移或生产写库。

## 3. 页面与交互设计

### 3.1 页面路由

沿用现有单页应用，不为登录页和用户管理新增独立 HTML 路由：

| 路由 | 页面 | 访问条件 |
|---|---|---|
| `/bond-factor-lab/` | 登录、因子实验室或用户管理视图 | 根据当前会话与角色决定 |

浏览器加载应用时先查询当前会话。查询完成以前只显示中性加载状态，不短暂展示 Dashboard，也不提前请求
Dashboard 数据。

- 当前会话有效：进入因子实验室；
- 当前会话无效：进入登录页；
- 管理员点击主导航中的“用户管理”时切换到用户管理视图；
- 普通用户不渲染用户管理入口，直接调用管理员 API 时由后端返回 `403`。

### 3.2 登录页

登录页延续现有米白背景、深色文字和红金强调色，只展示：

- Bond Factor Lab 标识；
- 用户名输入框；
- 密码输入框；
- 显示/隐藏密码按钮；
- 登录按钮；
- “账号由管理员创建；如需重置密码，请联系管理员”提示。

登录页不展示注册、忘记密码、第三方登录或任何 Dashboard 数据。

交互规则：

1. 支持键盘回车提交和密码管理器自动填充。
2. 请求期间禁用重复提交，并显示明确的进行中状态。
3. 用户名不存在、密码错误和账号停用不得返回可用于枚举账号的差异化文案。
4. 登录失败统一显示“用户名或密码错误”。
5. 登录成功后生成新会话，不复用登录前的任何会话标识。
6. 已登录用户访问登录页时直接回到因子实验室。

“记住我”在本系统中不能表示延长登录会话，所有会话始终固定为 12 小时。密码自动填充交给浏览器或独立密码
管理器：用户名输入框使用 `autocomplete="username"`，密码输入框使用 `autocomplete="current-password"`。应用不得把
密码写入 Cookie、`localStorage`、`sessionStorage`、IndexedDB 或服务端会话，也不通过自定义脚本读取并保存密码。

因此第一阶段不提供自定义“记住我”复选框。是否保存和自动填充密码由浏览器设置及其原生提示决定。

### 3.3 右上角账户入口

登录后的页面右上角只显示用户名，不展示头像：

```text
┌──────────────────────┐
│       zhangsan  ▾    │
└──────────────────────┘
             │
             ▼
       ┌────────────┐
       │ 个人资料   │
       │ 修改密码   │
       │ 退出登录   │
       └────────────┘
```

菜单严格只包含“个人资料”“修改密码”和“退出登录”。管理员的“用户管理”是应用主导航，不放入账户菜单。菜单必须支持：

- 鼠标点击打开；
- 键盘操作；
- `Escape` 关闭；
- 点击菜单外区域关闭；
- 正确维护 `aria-expanded`、焦点进入和焦点返回。

### 3.4 修改密码

点击“修改密码”打开对话框，包含：

- “密码不得少于6位，其中至少包含大写字母、小写字母和数字”提示；
- 当前密码；
- 新密码；
- 确认新密码；
- 取消；
- 确认修改。

修改成功后撤销该用户的全部会话，包括发起改密的当前浏览器会话，并返回登录页。首次登录和管理员重置密码后
都不强制修改密码；用户需要时从右上角主动进入该对话框。

### 3.5 退出登录

点击“退出登录”后：

1. 服务端撤销当前会话；
2. 浏览器清除会话 Cookie；
3. 清空前端内存中的 Dashboard 数据和当前用户状态；
4. 返回登录页；
5. 浏览器后退不得重新显示受保护数据。

### 3.6 管理员用户管理

管理员主导航增加“用户管理”。普通用户不显示该入口，后端仍必须在每次管理员 API 请求中验证角色。

用户列表展示：

| 字段 | 说明 |
|---|---|
| 用户名 | 管理员可以修改的登录名 |
| 用户姓名 | 可选；用户本人和管理员均可修改 |
| 机构名称 | 可选；用户本人和管理员均可修改 |
| 角色 | 管理员或普通用户 |
| 状态 | 正常或已停用 |
| 创建时间 | 账户创建时间 |
| 操作 | 编辑资料、修改用户名、编辑角色、重置密码、停用或恢复 |

新增用户对话框包含用户名、可选用户姓名、可选机构名称、初始密码和角色。新用户第一次登录后直接进入系统，
不强制修改初始密码。

“停用”必须二次确认。被停用用户立即失去访问权限，全部现有会话同时撤销。恢复只表示重新允许该账户登录：
用户继续使用停用前的密码，但必须重新登录；停用前已经撤销的浏览器会话不会自动重新生效。管理员认为原密码
不再安全时，应在恢复前后另外执行密码重置。

后端事务必须保证：

- 受保护的初始管理员不能被改名、改角色或停用；
- 管理员不能停用自己；
- 管理员不能把自己降为普通用户；
- 不能停用或降级最后一个有效管理员；
- 两名管理员并发操作时，也不能让有效管理员数量降为零。

`is_protected_admin` 只是对初始管理员增加不可改名、不可改角色、不可停用的保护，不引入第三种角色。管理员仍可
按已确认的两级角色模型创建其它管理员或调整非受保护账户；任何管理员都不能绕过受保护账户限制。

## 4. 角色与权限

| 能力 | `admin` | `user` |
|---|---:|---:|
| 登录和退出 | 是 | 是 |
| 查看全部因子实验室 Dashboard | 是 | 是 |
| 修改自己的密码 | 是 | 是 |
| 修改自己的姓名和机构 | 是 | 是 |
| 查看用户列表 | 是 | 否 |
| 创建用户 | 是 | 否 |
| 修改用户登录名 | 是 | 否 |
| 调整用户角色 | 是 | 否 |
| 重置用户密码 | 是 | 否 |
| 停用和恢复用户 | 是 | 否 |
| 算法激活、调度、迁移、补数或生产写库 | 否 | 否 |

角色由后端从数据库读取。前端不得提交、缓存或声明一个可被后端信任的角色。

## 5. 账户生命周期

### 5.1 用户名

- 长度为 3 至 32 个字符；
- 只允许小写英文字母、数字、点、下划线和连字符；
- 首字符必须是小写英文字母或数字；
- 创建前转为小写并按标准化结果检查唯一性；
- 管理员可以修改正常或已停用用户的用户名；
- 修改后的用户名必须重新执行格式与唯一性校验；
- 用户的内部身份始终是不可变的 `t_auth_users.id`，审计和关联关系不使用用户名作为主键；
- 用户名修改成功后写入变更前后值的审计记录，撤销该用户全部会话，并要求使用新用户名重新登录；
- 用户名未被修改前，即使账户已停用也继续占用原用户名；修改后旧用户名可以重新使用。

### 5.2 创建

管理员创建用户时指定用户名、初始密码和角色。初始状态为：

```text
status = active
must_change_password = false
```

管理员只能设置新密码，不能读取密码、密码哈希或用户旧密码。

### 5.3 密码重置

管理员重置密码时设置新的密码。成功后必须在同一事务中：

- 更新密码哈希；
- 保持 `must_change_password = false`；
- 撤销该用户全部会话；
- 写入审计日志。

### 5.4 停用与恢复

停用只修改状态并记录操作者与时间，不删除账户。停用时撤销的会话永久保持撤销；恢复只把账户重新设为可以
登录的正常状态，不会让旧浏览器自动恢复登录。用户可以继续使用原密码重新登录，管理员也可以另行重置密码。
恢复不修改历史审计记录，也不清除任何 session 的 `revoked_at` 或延长 `expires_at`。已撤销或已过期的 session 是
终态数据，任何账号恢复操作都不能令其重新生效。

## 6. 数据库设计

认证表位于各环境现有的 `bond_db`。Migration 022/023 只通过既有 `migrations.runner` 和
`scripts/apply_migrations.py` 管理 schema；当前阶段只授权按本文门槛在 ECS 独立数据库执行，Mac3 必须等待
用户明确确认 ECS 验收通过。

### 6.1 `t_auth_users`

| 字段 | 建议类型 | 约束/语义 |
|---|---|---|
| `id` | `BIGINT` | 自增主键 |
| `username` | `VARCHAR(32)` | 唯一、标准化小写用户名 |
| `full_name` | `VARCHAR(100)` | 可选用户姓名，空值为 `NULL` |
| `organization_name` | `VARCHAR(200)` | 可选机构名称，空值为 `NULL` |
| `password_hash` | `VARCHAR(255)` | Argon2id 编码结果 |
| `role` | `ENUM('admin','user')` | 两级角色 |
| `status` | `ENUM('active','disabled')` | 软删除状态 |
| `is_protected_admin` | `BOOLEAN` | 仅初始管理员为真；禁止页面/API 改名、改角色或停用 |
| `must_change_password` | `BOOLEAN` | 兼容保留，Migration 023 后固定为假 |
| `password_changed_at` | `DATETIME(6)` | 最近密码变更时间 |
| `created_by` | `BIGINT` | 创建者；初始管理员为空 |
| `disabled_by` | `BIGINT` | 停用操作者，可空 |
| `disabled_at` | `DATETIME(6)` | 停用时间，可空 |
| `created_at` | `DATETIME(6)` | 创建时间 |
| `updated_at` | `DATETIME(6)` | 最后更新时间 |

所有认证时间按 UTC 写入，展示时转换为 `Asia/Shanghai`。

### 6.2 `t_auth_sessions`

| 字段 | 建议类型 | 约束/语义 |
|---|---|---|
| `id` | `BIGINT` | 自增主键 |
| `user_id` | `BIGINT` | 关联 `t_auth_users.id` |
| `token_hash` | `BINARY(32)` | 随机会话令牌的 SHA-256 摘要，唯一 |
| `expires_at` | `DATETIME(6)` | 固定绝对过期时间 |
| `revoked_at` | `DATETIME(6)` | 撤销时间，可空 |
| `revoke_reason` | `VARCHAR(32)` | logout/password/username/status/role 等受控值 |
| `created_at` | `DATETIME(6)` | 会话创建时间 |

浏览器只持有原始随机会话令牌，数据库只保存摘要。每次成功登录都创建一条独立会话，因此同一用户可以在多个
浏览器同时登录。所有会话都从创建时起固定有效 12 小时，不在访问过程中自动续期。`revoked_at` 非空或
`expires_at` 已到期后，该会话永久无效。

### 6.3 `t_auth_audit_logs`

| 字段 | 建议类型 | 约束/语义 |
|---|---|---|
| `id` | `BIGINT` | 自增主键 |
| `actor_user_id` | `BIGINT` | 操作者；系统初始化可空 |
| `target_user_id` | `BIGINT` | 被操作账户，可空 |
| `event_type` | `VARCHAR(32)` | 创建、改用户名、改角色、重置密码、停用、恢复等受控值 |
| `request_id` | `VARCHAR(128)` | 与后端结构化日志关联 |
| `detail` | `JSON` | 不含密码、哈希、令牌和原始请求体的受控详情 |
| `created_at` | `DATETIME(6)` | 事件时间 |

审计表只记录已经提交成功的管理员账户变更和受保护管理员初始化/重置，且只允许 insert，不提供页面修改或删除
能力。登录、查询当前用户、读取用户列表和普通退出不重复写数据库审计表；必要的请求结果进入现有结构化服务日志。

### 6.4 写库边界

实施前必须同步更新根规范中的写库单点不变量：新增认证 repository 只能写 `t_auth_users`、
`t_auth_sessions` 和 `t_auth_audit_logs`，不得写 Registry、prediction、run、Actual、backtest 或源数据表；
现有 scheduler/backtest/updater 也不得写认证表。

## 7. 密码与会话安全

### 7.1 密码

- 使用 Argon2id，不使用明文、可逆加密、SHA-256 或 MD5 保存密码；
- 长度为 6 至 128 个字符；
- 必须至少包含一个 ASCII 大写字母、一个 ASCII 小写字母和一个数字；
- 特殊字符可以使用，但不强制要求；
- 不要求周期性改密；
- 支持复制粘贴和密码管理器；
- 密码、密码哈希和新密码不得进入日志、审计 `detail`、API 响应或应用管理的浏览器存储。

Argon2id 参数不得低于 OWASP 当前建议的最低安全基线，并在目标运行环境上验证登录延迟与资源占用。参考：
[OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

### 7.2 Cookie 与会话

生产会话 Cookie 固定使用以下安全属性：

```text
__Host-bfl-session=<opaque-token>; Secure; HttpOnly; SameSite=Strict; Path=/
```

- 不设置 `Domain`；
- 不把认证令牌写入 `localStorage`、`sessionStorage` 或 URL；
- 所有 Cookie 与服务端 session 都在创建 12 小时后绝对过期；
- 允许同一用户拥有多个并发的有效 session；
- 每次受保护请求都检查 session、过期时间、撤销状态、用户状态和当前角色；
- 普通退出只撤销当前 session；
- 用户改密、管理员重置密码、用户名变化、停用和角色变化立即撤销目标用户的全部 session；
- 恢复用户不得修改旧 session，不得让已过期或已撤销的 session 重新生效。

参考：[OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

### 7.3 CSRF 与来源校验

所有状态变更只接受 JSON `POST`，不得使用 `GET` 改变状态。后端必须严格校验受信任的 `Origin` 和
`Sec-Fetch-Site`，拒绝缺失或不匹配的浏览器写请求；`SameSite=Strict` 仅作为纵深防御。

参考：
[OWASP Cross-Site Request Forgery Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。

## 8. API 合同

后端内部路径使用下表中的 `/api/...`；经 Nginx 暴露时，公网/灰度浏览器路径统一加
`/bond-factor-lab` 前缀。为继续使用 Nginx 精确路径白名单，管理员操作使用固定 API 路径，不开放宽泛
`/api/` 前缀，也不依赖动态 URL 中的用户 ID。

### 8.1 认证 API

| 方法 | 路径 | 权限 | 作用 |
|---|---|---|---|
| `POST` | `/api/auth/login` | 匿名 | 验证用户名和密码并建立固定 12 小时会话 |
| `POST` | `/api/auth/logout` | 已登录 | 撤销当前会话 |
| `GET` | `/api/auth/me` | 匿名可调用 | 返回当前用户；无有效会话返回 `401` |
| `POST` | `/api/auth/change-password` | 已登录 | 修改自己的密码 |
| `POST` | `/api/auth/update-profile` | 已登录 | 修改自己的可选姓名和机构名称 |

### 8.2 管理员 API

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/admin/users` | 获取用户列表 |
| `POST` | `/api/admin/users` | 创建用户 |
| `POST` | `/api/admin/users/change-username` | 修改登录用户名 |
| `POST` | `/api/admin/users/change-role` | 修改用户角色 |
| `POST` | `/api/admin/users/reset-password` | 重置密码 |
| `POST` | `/api/admin/users/change-status` | 停用或恢复用户 |
| `POST` | `/api/admin/users/update-profile` | 修改用户的可选姓名和机构名称 |
| `POST` | `/api/admin/users/edit` | 在一个事务中编辑用户资料、权限、状态及可选新密码 |

管理员 API 每次都必须在后端验证当前会话与 `admin` 角色。前端隐藏入口不能替代授权检查。

### 8.3 状态码

| 状态码 | 语义 |
|---|---|
| `200` | 成功 |
| `201` | 用户创建成功 |
| `401` | 未登录、会话过期或会话已撤销 |
| `403` | 已登录但角色不足 |
| `409` | 用户名重复、最后管理员保护等业务冲突 |
| `422` | 输入不符合合同 |

## 9. 现有 Dashboard 接入

- 页面入口和静态 CSS/JS/SVG 可以匿名加载；
- `/api/auth/login` 和 `/api/auth/me` 允许未登录访问；
- `/api/health` 保持匿名，但只返回最小健康信息；
- `/api/factor-lab/dashboard` 的 Summary 与 Detail 均要求有效登录；
- `/api/admin/*` 只允许管理员；
- 未登录时前端不得发起 Dashboard 请求；
- 收到任一受保护 API 的 `401` 时清空前端业务状态并回到登录页；
- ECS 灰度入口验收合同从“匿名 Dashboard 返回 200”改为“匿名返回 401，登录后返回 200”。Mac3 公网合同只有
  在未来取得独立晋级授权后才改变。

## 10. 初始管理员与重置命令

Migration 只创建 schema，不写入默认用户名或密码。提供一次性、受控的初始化命令：

1. 仅在 `t_auth_users` 为空时允许执行；
2. 显式核对目标 database name 与 server UUID；
3. 用户名由操作者指定；
4. 初始密码从部署机权限受限的私有 secret 读取，必须符合统一密码规则，且不出现在仓库、命令行、shell history
   或日志；
5. 创建首个 `admin`，设置 `is_protected_admin = true`，首次登录不强制修改密码；
6. 用户表非空时 fail-closed；
7. 第一阶段只在 ECS 执行；Mac3 初始化属于未来独立晋级操作，不复制账户或密码。

唯一初始管理员忘记密码时不提供网页找回流程，只提供受控的管理员重置命令。该命令：

1. 只允许重置 `is_protected_admin = true` 的初始管理员，不能通过参数指定任意用户；
2. 与 migration apply 一样，要求显式核对目标 database name 与 server UUID；
3. 从部署机权限受限的私有 secret 读取符合统一密码规则的预先约定初始密码，不把密码写入仓库、命令参数、
   shell history 或日志；
4. 使用 Argon2id 重新生成密码哈希，并保持 `must_change_password = false`；
5. 在同一事务中撤销该管理员的全部现有会话并写入审计日志；
6. 重置后使用新密码重新登录；是否再次修改由用户自行决定。

受保护管理员的用户名、角色和状态不得通过用户管理页面或管理员 API 修改；不能将其停用、改名或降级。上述重置
命令是该账户唯一的离线恢复入口。私有 secret 的实际值属于部署凭据，不进入本文或版本控制。

## 11. 建议代码边界

- `backend.auth.routes`：只处理 HTTP 输入、输出和 Cookie；
- `backend.auth.service`：认证、角色、最后管理员保护和账户生命周期；
- `backend.auth.repository`：认证三张表的唯一数据库写入入口；
- `backend.auth.security`：密码哈希、令牌生成和恒定时间比较；
- 前端认证状态：只保存在运行内存，不保存认证令牌；
- Nginx：只增加已批准页面与 API 的精确 location。

模块不得读取或修改算法、Registry、prediction、Actual、backtest、DataBridge 或调度状态。

## 12. 验收标准

1. 未登录打开系统只显示登录页，不请求或显示 Dashboard 数据。
2. 未登录请求 Dashboard Summary/Detail 均返回 `401`。
3. 普通用户登录后可以正常使用现有 Dashboard。
4. 页面右上角只显示用户名；点击后显示“个人资料”“修改密码”和“退出登录”。
5. 普通用户看不到用户管理入口，直接调用管理员 API 返回 `403`。
6. 管理员可以创建普通用户和管理员，新用户首次登录不强制修改密码。
7. 用户本人和管理员都可以维护可选的用户姓名和机构名称，管理员列表能看到修改结果。
8. 管理员可以修改用户名、调整角色、重置密码、停用和恢复用户。
9. 修改用户名、停用、改角色、重置密码和用户改密后，目标用户在全部浏览器中的会话立即失效。
10. 并发管理操作也不能删除、停用或降级最后一个有效管理员。
11. 数据库、API 响应、日志和审计记录中不存在明文密码或原始会话令牌。
12. 管理员变更均有不可修改的审计记录。
13. Dashboard 数据合同、排序、统计和日期语义不因认证接入发生变化。
14. 第一阶段只在 ECS 独立认证数据中验收，不修改或同步 Mac3 账户数据。
15. ECS 不安装或开放 Nginx；Backend 只监听 loopback，并由 FastAPI 路由拒绝未列出的 API 方法，验收只经 SSH
    localhost 转发访问。
16. 本地单元、API、前端、migration、Nginx 合同和完整回归测试全部通过后，才可请求 ECS 现场 migration、
    release 激活和服务操作授权。
17. 同一用户可以在多个浏览器同时登录，且每条会话都在创建 12 小时后绝对过期。
18. 恢复用户不会改变旧会话的过期或撤销状态，任何旧会话都不能因此恢复有效。
19. 管理员重置命令拒绝不符合统一密码规则的初始密码，不从参数、输出、日志或版本控制中暴露密码，并在重置后
    撤销管理员全部会话。

## 13. ECS 第一阶段实施与验收边界

第一阶段按“当前工作区实现和自动化验证 → 构建不可变 release → ECS 独立灰度集成验收”推进：

1. 在当前 `codex/develop` 代码线上实现，先完成认证单元/API/前端测试、Migration 022 隔离 MySQL 测试、Nginx
   精确白名单测试和现有完整回归；
2. `requirements-service.txt` 增加固定版本的 Argon2id 实现依赖，并在 ECS 的
   `bond_factor_lab_service` 环境中按受控依赖变更流程安装；
3. 只从 clean commit 构建 deterministic archive，ECS 仍从 `/opt/bond-factor-lab/current` 的不可变 release 运行，
   不在 ECS `current` 或 release 目录现场改代码；
4. Migration 022 只在 ECS `bond_db` 上经 `scripts/apply_migrations.py` 执行，并显式核对 ECS 的 database name 与
   server UUID；不连接或修改 Mac3 数据库；
5. 初始管理员密码只在 ECS 部署机私有 secret 中配置，初始化与重置命令不得从命令参数接收密码；
6. ECS Backend 继续只监听 `127.0.0.1:8100`，不得为测试直接开放该端口或扩大安全组；浏览器通过 SSH 本地
   转发访问 `http://localhost:18110`，验证 localhost Secure Cookie、CSRF 来源校验和完整前端交互；
7. ECS release 通过外置配置声明唯一受信任 Origin `http://localhost:18110`；该 HTTP 例外只允许
   `aliyun-gray` 的精确 localhost 灰度入口，Cookie 仍必须保留 `Secure`；
8. 登录功能不修改或重启 DataBridge、prediction、Actuals timer，也不改变 ECS 的单 Writer 控制面；
9. ECS 验收通过不自动授权 Mac3 晋级。未来 Mac3 必须复用同一份已验证 archive，并分别取得 migration、secret、
   Nginx、release 激活和服务操作授权。

ECS 验收完成后必须停止并等待用户确认；Mac3 只能使用同一份已验证 archive，并独立执行 migration、secret、
生产 Nginx、release 激活和 backend 重启。Mac3 登录切换后的失败回滚采用安全优先策略：入口临时返回 503，
不得恢复旧版匿名 Dashboard。
