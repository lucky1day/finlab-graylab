本文档记录 2026-06-09 架构评审后、2026-06-10 落地改造过程中遇到的真实问题，避免后续新增方案时重复踩坑。

## 坑 0（最关键）：回测与实盘的 predict_date 含义不同，误用会导致数据泄漏

**严重等级**：Critical。理解错误会导致回测高估准确率（数据泄漏），或实盘预测使用了未来数据。

**回测与实盘的 predict_date 差异**：

| 模式 | predict_date | 特征数据截止 | target_date | 说明 |
|------|-------------|-------------|-------------|------|
| **回测** | T | T（当日收盘数据） | T+N（经 N 个交易日） | 模拟在 T 日收盘后立即预测 |
| **实盘** | T+1 | T（收盘数据齐全后） | T+N（与回测相同的 target） | 等 T 日完整数据到位后，在 T+1 日开盘前预测，但 target 仍然是 T+N |

**核心区别**：回测和实盘预测的 **target 是同一个日期**（T+N），但 **predict_date 不同**。

- **回测**：`predict_date = T`，在 T 收盘后用 T 的数据预测 T+N。
- **实盘**：`predict_date = T+1`，在 T+1 开盘前用 T 的齐全数据预测同样的 T+N。
- `target_date` 由特征数据的截止日期 + horizon 确定，**不是由 predict_date + horizon 确定**。

**关键约束**：

1. **`predict_date` 只表示"预测发出的实际日期"，不用于计算 target。** `target_date` 的计算基于特征数据日期 + horizon，与 `predict_date` 无关。

2. **前端只看 `target_date` 的结果是否正确**，不关心 `predict_date` 是 T 还是 T+1。回测和实盘的 target_date 在同一个时间轴上，可直接对比。

3. **`predict_date` 不能伪造。** 实盘的 `predict_date` 必须等于实际发出预测的日期（如 T+1 日 07:03），不能设为 T（特征数据截止日）。否则在回测中评估时，如果回测按 T+1 跑但 predict_date 标为 T，会导致回测结果无法与实盘对齐。

**数据泄漏风险**：
- `predict_date` 不影响 `target_date`（target 由特征数据日期决定）。
- 但如果实盘的 `predict_date` 标为 T（实际是 T+1 发出的），在追溯时会造成混淆——你以为 T 日发出的预测，其实是 T+1 日才发出的，T+1 日的部分行情可能已经影响了模型。
- 当前实盘在 07:03 开盘前执行，此时 T 日数据已齐全且当日行情尚未开始，所以 `predict_date = T` 不会看到未来数据。但如果未来调度时间改到盘中或收盘后，必须重新评估。

**检查清单**（新增方案时逐项核对）：
- [ ] `target_date` 的计算是否基于特征数据日期 + horizon？
- [ ] `predict_date` 是否等于实际发出预测的日期（不是特征数据截止日期）？
- [ ] 实盘和回测的 `target_date` 是否指向同一个时间轴？
- [ ] 新增方案时 adapter 中是否明确区分了 `predict_date` 和 `target_date` 的语义？

## 坑 1：predict_date 与 target_date 口径不一致

**现象**：前端明细、月度指标、回测预计算、去重逻辑四处用了四种不同的日期分组方式，导致同一组数据显示不一致。

**涉及文件**：
- `backend/services.py:_scheme_metric_month` ← 用 predict_date
- `backend/services.py:_prediction_point_date` ← 用 predict_date
- `frontend/aifin-shell.js:detailGroupMonth` ← 用 predict_date
- `frontend/aifin-shell.js:detailDisplayDay` ← 用 predict_date

**根因**：每个模块独立实现了自己的月份归属逻辑，没有一个中心约定说"展示和分组统一用哪个日期字段"。改动时只改了前端，忘了后端和回测。

**修复**：全部改为 `target_date`（参见 SOP §1.0 规则一）。修复涉及 5 个文件、4 个模块（前端、后端 metrics、后端 dedup、回测 runner）。

**检查清单**（新增方案或修改方案时逐项核对）：

## 坑 2：Serving pointer 覆盖导致数据消失

**现象**：同一 predict_date 重新跑预测后，serving pointer 被覆盖，旧 prediction（不同 target_date）不再被任何查询命中，在前端消失。

**历史涉及文件**（该问题已修复；当前代码不再依赖 serving pointer 作为读取路径）：
- `scheduler/repository.py:update_serving_pointer`
- `backend/services.py` 中所有 `INNER JOIN t_scheme_serving_pointer`

**根因**：Serving pointer 的 UK 是 `(scheme_id, target_tenor, predict_date)`。同一天跑两轮预测时，第二轮覆盖第一轮的指针，但两轮可能有不同的 `target_date`。旧 `target_date` 的 prediction 行还在表中，但因为指针指向了新 run_id，被 `INNER JOIN` 排除。

**修复**：
1. 将 `t_scheme_predictions` 的 UK 改为 `(scheme_id, target_tenor, horizon, target_date)` + UPSERT（覆盖旧 prediction）。
2. 删除后端所有 `INNER JOIN t_scheme_serving_pointer` 查询，直接读 `t_scheme_predictions`。
3. UK 自身保证唯一性，不需要额外过滤层。

**教训**：如果数据模型已经用 UK + UPSERT 保证了唯一性，不要在上面再叠一层外部指针表。额外的间接层不会增加安全性，只会引入数据不一致。

## 坑 3：ActivationGate 不认 `skipped` 为通过

**现象**：CompareGate 因 benchmark 样本文件缺失返回 `skipped`（passed=true），但 ActivationGate 仅检查 `status == "passed"`，认为 compare gate 未通过，阻止激活。

**涉及文件**：
- `harness/gates/activate_gate.py:REQUIRED_ACTIVATE_GATES` 检查逻辑

**根因**：`skipped` 不是 `failed`——它表示"条件不具备，跳过检查"。但激活检查只认 `passed`。

**修复**：`activate_gate.py` 中将 `passed_gates` 的判定条件从 `row[1] == "passed"` 改为 `row[1] in ("passed", "skipped")`。

**教训**：Gate 的 `skipped` 状态只意味着"该 gate 本次没有执行"。框架层可以在不适用的 gate 上兼容 `skipped`，但新增 source-backed 方案的 CompareGate 不适用这一放行语义：只要存在原始脚本、原始输出或人工 benchmark，CompareGate 必须通过 `passed`，不能把 `skipped` 当作完成证据（见坑 11）。

## 坑 4：周度实盘预测需要目标周数据存在才能运行

**现象**：周六运行周度预测时，下一周的数据尚未进入 `api_wind_weekly`，算法因找不到目标周（`feature_week_id + 1`）的数据而回退到当前周，产出错误的 target_date。

**涉及文件**：
- `schemes/weekly_5y_direct_0529/predict.py`

**根因**：`end_week = current_week_id + 1` 限制了数据加载范围。算法逻辑中 `(feature_week_id + 1) in all_weeks_set` 要求目标周必须存在数据。实盘模式下目标周数据尚未可用，检查失败导致回退。

**修复**：
1. `end_week` 设为 `current_week_id + 6`，确保特征数据加载范围足够。
2. 如果 `feature_week_id` 是数据中最新的周，允许以其下一周作为 target（即使数据不存在）。

**检查清单**：
- [ ] `predict.py` 中 `end_week` ≥ `current_week_id + 6`
- [ ] 目标周数据不存时仍能正常预测
- [ ] `all_weeks_set` 检查不能硬拦最新周的下一周

## 坑 11：方案激活时跳过了"源文件原始回测 vs 入库后回测"对比

**严重等级**：Critical。跳过该对比等于上线了未经行为验证的方案——平台改造可能悄悄改变了算法行为而无人发现。

**现象**（实际发生）：`weekly_7y_cross_d_overlay_0529` 首次入库时，因为 `schemes/{id}/benchmarks/` 目录没有 benchmark 文件，CompareGate 返回 `skipped`。由于 ActivationGate 把 `skipped` 视同通过（坑 3 的修复），方案被直接激活上线。"源文件原始脚本输出 vs 入库后框架输出"的逐样本对比完全没有发生，事后才补做。

**根因链条**：
1. `generate_benchmark_samples.py` 只支持日频方案，周频方案的 benchmark 文件需要手工准备——容易被遗漏。
2. CompareGate 缺文件时 `skipped` 不阻断 `onboard --stage all`。
3. ActivationGate 接受 `skipped`（坑 3 修复的副作用）——本意是放过"无基准的纯实验方案"，但也放过了"有基准却没准备文件"的方案。
4. SOP 的 Step 10 激活条件没有显式列出"源 vs 入库对比必须完成"。

**修复**：
1. SOP 新增 **Step 10a（强制）**：激活前必须完成 POST_ONBOARDING_TEST_SOP 的 S3–S5（源脚本基准 → 框架复现 → 方向零容差对比），benchmark 文件落位，CompareGate 必须 `passed` 而非 `skipped`。
2. 新方案 `config.yaml` 必须设 `backtest.benchmark_required: true`，使 CompareGate 缺文件时 FAIL 而非 SKIP。
3. 对比证据（matched 数、direction diff）必须写入 `CURRENT_STATUS.md`。

**事后补做的对比结果**（weekly_7y_cross_d_overlay_0529）：
- 源脚本窗口 43 条样本 vs DB run_id=89：matched 43/43，direction/label/confidence/target_date 全部零差异。
- 补齐四份 benchmark 文件 + `benchmark_required: true` 后重跑 onboard，CompareGate `passed`（direction_match_rate=1.0）。

**检查清单**（每个新方案激活前逐项核对）：
- [ ] POST_ONBOARDING_TEST_SOP S3：源文件原始脚本（或静态基准）已跑出基准序列
- [ ] S4：入库后框架代码已跑出复现序列（同一数据接入层）
- [ ] S5：逐样本对比，方向零容差，全部 matched
- [ ] `schemes/{id}/benchmarks/` 四份文件齐全
- [ ] `config.yaml` 含 `backtest.benchmark_required: true`
- [ ] `harness onboard --stage all` 中 CompareGate 状态为 `passed`（不是 `skipped`）
- [ ] 对比证据已写入 `CURRENT_STATUS.md`

## 坑 12：方案激活后未回补实盘预测，前端缺失实盘观察序列

**现象**（实际发生）：`weekly_7y_cross_d_overlay_0529` 激活后，前端没有"实盘发出起点"分隔线，缺少 6月6日预测的 06/12"待验证"行。第一次补救时只补了 `predict_date=2026-06-06 -> target_date=2026-06-12`，前端 2026-06 周度表仍缺 `target_date=2026-06-05`；实际还必须补 `predict_date=2026-05-30 -> target_date=2026-06-05`。原因是激活时只完成了回测落库，没有补跑灰度起点（2026-06-01）以来应当存在的实盘预测。

**根因**：方案在灰度起点之后才入库，错过了此前的调度窗口。回补时如果按 `predict_date >= 2026-06-01` 枚举，会漏掉周度 6 月第一条目标周，因为 `target_date=2026-06-05` 的预测发出日是上一轮周六 `predict_date=2026-05-30`。激活只让"未来"的调度生效，不会自动补"过去"缺失的预测。

**修复**：SOP 新增 **Step 10b（强制）**：激活后必须按调度日历回补 target_date 从 2026-06-01 至今的全部实盘预测，先枚举应有 `target_date`，再反推对应 `predict_date`。`predict_date` 可以早于灰度起点；禁止只按 `predict_date` 起点过滤。

**前端联动逻辑**（无需改前端代码，数据补齐后自动生效）：
- "实盘发出起点"分隔线：周度方案 = 第一条实盘 target 月份首日之前的周六（如 target 在 6月 → 2026-05-30）；日频方案 = 第一条实盘 predict_date。
- 尚无 actuals 的 target 自动显示"待验证"。

**检查清单**（激活后逐项核对）：
- [ ] DB 中实盘预测 target_date 连续覆盖 2026-06-01 至今
- [ ] 周频方案 6 月第一条 target（例如 2026-06-05）已存在，即使其 predict_date 是 2026-05-30

## 坑 14：CompareGate 的 confidence 差异术语不清，容易被误解成平台新指标

**现象**（实际发生）：`weekly_10y_d_overlay_0529` CompareGate 通过后，报告里出现 `max_confidence_abs_diff=1.1102230246251565e-16`。用户追问“最大 confidence 差异是什么？原本的文件就有 confidence？”说明文档没有讲清 `confidence` 的来源和比较含义。

**根因**：
1. `PredictionRecord.confidence` 是平台统一字段，但不同原始算法可能叫 `confidence`、`probability`、`score` 或 `prob_up`。
2. CompareGate 只比较 original/current benchmark CSV 中同名 `confidence` 字段的数值差，并不判断这个值的金融含义。
3. 浮点计算从原始脚本迁移到框架后，可能出现 `1e-16` 量级的二进制舍入差异；这不是算法行为差异。
4. SOP 只写了“confidence diff”，没有说明该字段是原始算法输出的归一化承接字段，也没有说明缺失时如何处理。

**修复**：
1. T0 / SOP / SCHEME_CONTRACT 明确：`confidence` 承接原始算法已有置信度、概率或分数；不是平台新增标签。
2. 如果原始算法没有天然 `confidence`，original/current benchmark 必须使用同一确定性代理值，并在 `CURRENT_STATUS.md` 写清映射。
3. CompareGate 的硬门槛是 `predicted_direction` 零容差；`max_confidence_abs_diff` 只做辅助一致性检查，`1e-16` 量级按 0 看待。
4. benchmark CSV 的必需字段继续保留 `predict_date/tenor/direction/confidence`；周度方案额外保留 `feature_week_id/target_date` 方便审计，但月份归属仍按 `target_date`。

**检查清单**：

## 坑 15：前端 helper 直测通过，但候选排行真实对象字段名不同

**现象**（实际发生）：`weekly_7y_cross_d_overlay_0529` 和 `weekly_10y_d_overlay_0529` 已在 `SCHEME_DEPLOYMENT_DATE_OVERRIDES` 配置为 `2026/06/10`，单测直接调用 `getSchemeDeploymentDate({ scheme_id })` 也通过，但前端候选方案排行仍显示默认 `2026/06/01`。

**根因**：后端 API 原始对象使用 `scheme_id`，但进入候选排行前，前端会把对象归一为 `schemeId`。`getSchemeDeploymentDate()` 只识别 `scheme_id`，在真实排行 row 中无法命中 override，于是回退到对象上已经固化的默认 `deploymentDate=2026/06/01`。

**修复**：
1. `getSchemeDeploymentDate()` 同时识别 `scheme_id`、`schemeId` 和精确匹配的 `id`。
2. 单测必须覆盖真实排行对象形态：`schemeId + deploymentDate=2026/06/01`，并断言渲染出的候选排行行显示 `2026/06/10`。

**检查清单**：
- [ ] 测试不能只直测 helper 的 API 原始字段形态，还要测真实 render row 的归一化对象。
- [ ] 前端展示字段如果有 API 原始态与 UI 归一态两种对象，helper 必须兼容两种字段名。
- [ ] 部署时间仍只是展示字段，不参与 `target_date` 分组、回测截断、实盘回补或唯一键。

## 坑 16：静态前端文件被浏览器缓存，代码已修但页面仍显示旧值

**现象**（实际发生）：`frontend/aifin-shell.js` 已修复并通过测试，7Y/10Y 周度候选排行部署时间应为 `2026/06/10`，但用户前端页面仍显示旧默认值 `2026/06/01`。用户执行浏览器强制刷新后，页面立即恢复正确。

**根因**：前端为 FastAPI serve 的静态 HTML/JS。浏览器可能缓存旧版 `aifin-shell.js`，导致用户看到的页面逻辑不是当前工作区最新文件。此类问题容易被误判为代码或 API 未生效。

**处理顺序**：
1. 只要刚修改过 `frontend/*.js` 或 `frontend/*.html`，而用户页面仍显示旧内容，第一时间提醒用户强制刷新。
2. macOS 推荐 `Cmd+Shift+R`；若仍不生效，打开 DevTools，勾选 `Disable Cache` 后刷新。
3. 缓存排除后再继续查 API payload、后端服务进程、静态文件路径或代码逻辑。

**检查清单**：
- [ ] 前端显示与已提交代码不一致时，先问/提醒是否强制刷新。
- [ ] 验收前端静态资源改动时，使用强制刷新或禁用缓存后的页面作为证据。
- [ ] 文档或最终回复中避免直接断言“前端仍错”是代码问题，先排除浏览器缓存。
