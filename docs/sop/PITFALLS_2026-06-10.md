本文档记录 2026-06-09 架构评审后、2026-06-10 落地改造过程中遇到的真实问题，避免后续新增方案时重复踩坑。

## 坑 0（最关键）：回测与实盘的 predict_date / feature_date 含义不同，误用会导致数据泄漏

**严重等级**：Critical。理解错误会导致回测高估准确率（数据泄漏），或实盘预测使用了未来数据。

**回测与实盘的日期差异**：

| 模式 | prediction_phase | predict_date | feature_date | target_date | 说明 |
|------|------------------|-------------|--------------|-------------|------|
| **回测** | 不写入实盘 phase | T | T | T+N | 模拟在 T 日用 T 的数据预测 |
| **灰度实盘** | `gray_live` | T+1 | T | T+N | 事后补齐/观察，也算实盘，但只能使用 T 及以前数据 |
| **正式实盘** | `scheduled_live` | T+1 | T | T+N | scheduler 在真实时钟自然触发 |

**核心区别**：回测和实盘预测的 **target 是同一个日期**（T+N），但 **predict_date 不同**。平台和业务统一使用 `feature_date` 表示数据截止日；`anchor_date` 只允许作为方案内部变量或审计 extra，且必须等于 `feature_date`。

- **回测**：`predict_date = feature_date = T`。
- **实盘**：`predict_date = T+1`，`feature_date = T`。
- `target_date` 由 `feature_date + horizon` 确定，**不是由 predict_date + horizon 确定**。

**关键约束**：

1. **`predict_date` 只表示"预测发出的实际日期"，不用于计算 target。** `target_date` 的计算基于 `feature_date + horizon`，与 `predict_date` 无关。

2. **前端评价正确性、月份归属和回测/实盘对比统一按 `target_date`**；需要展示数据截止或预测站位时统一使用 `feature_date`。回测和实盘的 target_date 在同一个时间轴上，可直接对比。

3. **`predict_date` 和 `feature_date` 都不能伪造。** 实盘的 `predict_date` 必须等于应当发出预测的日期（如 T+1 日 07:03），`feature_date` 必须等于 T；回测则必须 `predict_date == feature_date`。

**数据泄漏风险**：
- `predict_date` 不影响 `target_date`（target 由 `feature_date` 决定）。
- 灰度补齐是事后运行，当前 DB 可能已经拥有 T+1 或更晚数据；如果输入 artifact 没有硬性截到 `feature_date=T`，就会产生隐性数据泄漏。
- 只有 scheduler 在真实时钟自然触发且输入截止到 `feature_date` 的记录，才能标识为 `scheduled_live`。

**检查清单**（新增方案时逐项核对）：
- [ ] `target_date` 的计算是否基于特征数据日期 + horizon？
- [ ] `feature_date` 是否是前端/业务使用的唯一数据截止字段？
- [ ] `predict_date` 是否等于实际发出预测的日期（不是特征数据截止日期）？
- [ ] 灰度补齐是否标识 `prediction_phase=gray_live`，正式调度是否标识 `scheduled_live`？
- [ ] 实盘和回测的 `target_date` 是否指向同一个时间轴？
- [ ] 新增方案时 adapter 中是否明确区分了 `predict_date` 和 `target_date` 的语义？

## 坑 0b：V28 这类 test window 敏感算法不能把窗口当普通参数

**严重等级**：Critical。同一个 `feature_date`，只要 core 的 test window 不同，输出就可能改变；这会造成 benchmark 通过一套口径、实盘写入另一套口径。

**现象**（实际发生）：`daily_5y_2_v28` 的 source May 2026 benchmark 中，`feature_date=2026-05-28` 的方向为 `1`。平台灰度实盘旧 `run_id=42` 却写出了不同方向，导致 source benchmark 与 `t_scheme_predictions.feature_date` 对齐核验失败。

**根因**：源算法按“月度 test window”运行。V28 core 的 Phase C 会基于 `test_months` 做 monthly ensemble / signal selection，所以 `2026-05-01..2026-05-28` 与连续窗口 `2024-07-01..2026-05-28` 不是同一个算法输入。旧平台 wrapper 把窗口当成普通回测范围，导致 `predict.py` 与回测/benchmark 口径不一致。

**修复**：
1. 新增 `schemes.daily_5y_2_v28.inference` 作为唯一核心预测入口。
2. `v28_feature_month_window(feature_date)` 固定返回 `feature_date` 所在月第一天到 `feature_date`，不得越过 `feature_date`。
3. `predict.py`、gray/live 补齐、benchmark current 生成和 backtest runner 均调用同一个 inference helper。
4. V28 benchmark current 由 `scripts/rebuild_v28_scheme_benchmark.py` 调平台 helper 生成，不复制 source CSV。
5. 旧错误 `run_id=42` 的 V28 灰度预测明细已删除，保留 run/log 审计；新 `run_id=58` 写入 `predict_date=2026-05-29`、`feature_date=2026-05-28`、`target_date=2026-06-04`、`predicted_direction=1`、`confidence=1.0`。

**检查清单**：
- [ ] 方案是否存在 test-window-sensitive 的 selector、ensemble、rolling top-K、分月校准或信号组合逻辑？
- [ ] adapter 与 backtest runner 是否调用同一个 inference helper？
- [ ] live/gray 的核心窗口是否以 `feature_date` 截止，而不是当前 DB 最新日？
- [ ] source benchmark 的 `date/T` 是否对齐 `feature_date`，而不是实盘 `predict_date`？
- [ ] benchmark current 侧是否由平台 helper 生成，且 strict key 逐行一致？

**检查清单**（新增方案或修改方案时逐项核对）：

## 坑 2：Serving pointer 覆盖导致数据消失

**现象**：同一 predict_date 重新跑预测后，serving pointer 被覆盖，旧 prediction（不同 target_date）不再被任何查询命中，在前端消失。

**历史涉及文件**（该问题已修复；当前代码不再依赖 serving pointer 作为读取路径，`update_serving_pointer` helper 已删除）：
- 旧版 `scheduler/repository.py:update_serving_pointer`
- 旧版 `backend/services.py` 中所有 `INNER JOIN t_scheme_serving_pointer`

**根因**：Serving pointer 的 UK 是 `(scheme_id, target_tenor, predict_date)`。同一天跑两轮预测时，第二轮覆盖第一轮的指针，但两轮可能有不同的 `target_date`。旧 `target_date` 的 prediction 行还在表中，但因为指针指向了新 run_id，被 `INNER JOIN` 排除。

**修复**：
1. 将 `t_scheme_predictions` 的 UK 改为 `(scheme_id, target_tenor, horizon, target_date)` + UPSERT（覆盖旧 prediction）。
2. 删除后端所有 `INNER JOIN t_scheme_serving_pointer` 查询，直接读 `t_scheme_predictions`。
3. UK 自身保证唯一性，不需要额外过滤层。

**教训**：如果数据模型已经用 UK + UPSERT 保证了唯一性，不要在上面再叠一层外部指针表。额外的间接层不会增加安全性，只会引入数据不一致。

## 坑 3：ActivationGate 不认 `skipped` 为通过

**现象**：CompareGate 因 benchmark 样本文件缺失返回 `skipped`（passed=true），但 ActivationGate 仅检查 `status == "passed"`，认为 compare gate 未通过，阻止激活。

**涉及文件**：
- `harness/gates/activate_gate.py:REQUIRED_ACTIVATE_GATES` 检查逻辑

**根因**：`skipped` 不是 `failed`——它表示"条件不具备，跳过检查"。但激活检查只认 `passed`。

**修复**：`activate_gate.py` 中将 `passed_gates` 的判定条件从 `row[1] == "passed"` 改为 `row[1] in ("passed", "skipped")`。

**教训**：Gate 的 `skipped` 状态只意味着"该 gate 本次没有执行"。框架层可以在不适用的 gate 上兼容 `skipped`，但新增 source-backed 方案的 CompareGate 不适用这一放行语义：只要存在原始脚本、原始输出或人工 benchmark，CompareGate 必须通过 `passed`，不能把 `skipped` 当作完成证据（见坑 11）。

## 坑 4：周度实盘预测误读未来周数据或要求目标周数据存在

**现象**：周六运行周度预测时，下一周的数据尚未进入 `api_wind_weekly`。旧写法一度为了让目标周存在而扩大 `end_week` 到未来周，或在找不到目标周时回退到当前周，都会污染 `target_date` 语义，并可能在灰度补齐时读到 `feature_date` 之后的周频修订数据。

**涉及文件**：
- `schemes/weekly_5y_direct_0529/predict.py`

**根因**：把 target 周当成输入数据的一部分。live/gray 的输入截止应该是 `feature_date`，特征周应该是 `feature_week_id`；目标周只用于生成 `target_week_id/target_date`，不能要求目标周数据已入库，也不能为了凑 target 周读取未来周。

**修复**：
1. live/gray 周频 artifact 必须传 `end_week=feature_week_id`、`as_of_date=feature_date`，只读取 `feature_date` 及以前可见的周频原始行。
2. `target_week_id/target_date` 只能由 DB 日历从 `feature_week_id` 推导到下一实际周及其最后交易日，不依赖 `api_wind_weekly` 中是否已有目标周数据。

**检查清单**：
- [ ] live/gray adapter 调用 weekly artifact 时使用 `end_week=feature_week_id`
- [ ] live/gray adapter 调用 weekly artifact 时使用 `as_of_date=feature_date`
- [ ] 目标周数据不存时仍能正常预测
- [ ] `target_week_id/target_date` 来自 DB 日历，而非 `feature_week_id + 1` 公式或 `all_weeks_set` 目标周存在性检查

## 坑 11：方案激活时跳过了"源文件原始回测 vs 入库后回测"对比

**严重等级**：Critical。跳过该对比等于上线了未经行为验证的方案——平台改造可能悄悄改变了算法行为而无人发现。

**现象**（实际发生）：`weekly_7y_cross_d_overlay_0529` 首次入库时，因为 `schemes/{id}/benchmarks/` 目录没有 benchmark 文件，CompareGate 返回 `skipped`。由于 ActivationGate 把 `skipped` 视同通过（坑 3 的修复），方案被直接激活上线。"源文件原始脚本输出 vs 入库后框架输出"的逐样本对比完全没有发生，事后才补做。

**根因链条**：
1. `generate_benchmark_samples.py` 只支持日频方案，周频方案的 benchmark 文件需要手工准备——容易被遗漏。
2. CompareGate 缺文件时 `skipped` 不阻断 `onboard --stage all`。
3. ActivationGate 接受 `skipped`（坑 3 修复的副作用）——本意是放过"无基准的纯实验方案"，但也放过了"有基准却没准备文件"的方案。
4. SOP 的 Step 10 激活条件没有显式列出"源 vs 入库对比必须完成"。

**修复**：
1. SOP 新增 **Step 10a（强制）**：激活前必须完成 POST_ONBOARDING_TEST_SOP 的 S3–S5（源脚本基准 → 框架复现 → 方向零容差对比），benchmark 文件落位，CompareGate 必须 `passed` 而非 `skipped`。
2. 新方案 `config.yaml` 必须设 `backtest.benchmark_required: true`，使 CompareGate 缺文件时 FAIL 而非 SKIP。
3. 对比证据（matched 数、direction diff）必须写入 `CURRENT_STATUS.md`。

**事后补做的对比结果**（weekly_7y_cross_d_overlay_0529）：
- 初始源脚本窗口 43 条样本 vs DB run_id=89：matched 43/43，direction/label/confidence/target_date 全部零差异。
- 2026-06-13 周频历史回测统一排除灰度实盘 target 后，历史 benchmark 覆盖窗口保留 `target_date < 2026-06-01` 的 42 条；latest run_id=110 的 `original_benchmark_validation` 为 42/42 matched。
- 补齐四份 benchmark 文件 + `benchmark_required: true` 后重跑 onboard，CompareGate `passed`（direction_match_rate=1.0）。

**检查清单**（每个新方案激活前逐项核对）：
- [ ] POST_ONBOARDING_TEST_SOP S3：源文件原始脚本（或静态基准）已跑出基准序列
- [ ] S4：入库后框架代码已跑出复现序列（同一数据接入层）
- [ ] S5：逐样本对比，方向零容差，全部 matched
- [ ] `schemes/{id}/benchmarks/` 四份文件齐全
- [ ] `config.yaml` 含 `backtest.benchmark_required: true`
- [ ] `harness onboard --stage all` 中 CompareGate 状态为 `passed`（不是 `skipped`）
- [ ] 对比证据已写入 `CURRENT_STATUS.md`

## 坑 12：方案激活后未回补实盘预测，前端缺失实盘观察序列

**现象**（实际发生）：`weekly_7y_cross_d_overlay_0529` 激活后，前端没有"实盘发出起点"分隔线，缺少 6月6日预测的 06/12"待验证"行。第一次补救时只补了 `predict_date=2026-06-06 -> target_date=2026-06-12`，前端 2026-06 周度表仍缺 `target_date=2026-06-05`；实际还必须补 `predict_date=2026-05-30 -> feature_date=<上一完整周> -> target_date=2026-06-05`。原因是激活时只完成了回测落库，没有补跑灰度起点（2026-06-01）以来应当存在的灰度实盘预测。

**根因**：方案在灰度起点之后才入库，错过了此前的调度窗口。回补时如果按 `predict_date >= 2026-06-01` 枚举，会漏掉周度 6 月第一条目标周，因为 `target_date=2026-06-05` 的预测发出日是上一轮周六 `predict_date=2026-05-30`。激活只让"未来"的调度生效，不会自动补"过去"缺失的预测。

**修复**：SOP 新增 **Step 10b（强制）**：激活后必须按调度日历回补 target_date 从灰度起点至今的全部灰度实盘预测，先枚举应有 `target_date`，再反推对应 `predict_date` 和 `feature_date`。`predict_date` 可以早于灰度起点；禁止只按 `predict_date` 起点过滤。补齐记录必须标识 `prediction_phase=gray_live`。

**前端联动逻辑**（无需改前端代码，数据补齐后自动生效）：
- "实盘发出起点"分隔线：日频和周度统一取该方案 live rows 的最小 `predict_date`；灰度区间和正式调度起点由 `/api/metrics/{scheme_id}` 的 `phase_ranges` 展示。
- 尚无 actuals 的 target 自动显示"待验证"。

**检查清单**（激活后逐项核对）：
- [ ] DB 中实盘预测 target_date 连续覆盖 2026-06-01 至今

## 坑 14：CompareGate 的 confidence 差异术语不清，容易被误解成平台新指标

**现象**（实际发生）：`weekly_10y_d_overlay_0529` CompareGate 通过后，报告里出现 `max_confidence_abs_diff=1.1102230246251565e-16`。用户追问“最大 confidence 差异是什么？原本的文件就有 confidence？”说明文档没有讲清 `confidence` 的来源和比较含义。

1. `PredictionRecord.confidence` 是平台统一字段，但不同原始算法可能叫 `confidence`、`probability`、`score` 或 `prob_up`。
2. CompareGate 只比较 original/current benchmark CSV 中同名 `confidence` 字段的数值差，并不判断这个值的金融含义。
3. 浮点计算从原始脚本迁移到框架后，可能出现 `1e-16` 量级的二进制舍入差异；这不是算法行为差异。
4. SOP 只写了“confidence diff”，没有说明该字段是原始算法输出的归一化承接字段，也没有说明缺失时如何处理。

**修复**：
1. T0 / SOP / SCHEME_CONTRACT 明确：`confidence` 承接原始算法已有置信度、概率或分数；不是平台新增标签。
2. 如果原始算法没有天然 `confidence`，original/current benchmark 必须使用同一确定性代理值，并在 `CURRENT_STATUS.md` 写清映射。
3. CompareGate 的硬门槛是 `predicted_direction` 零容差；`max_confidence_abs_diff` 只做辅助一致性检查，`1e-16` 量级按 0 看待。
4. benchmark CSV 的必需字段改为 `feature_date(or source_t)/target_date/tenor(or target_tenor)/direction/confidence`；历史旧列名 `predict_date/date` 只能解释为 source T / 平台 `feature_date`。周度方案额外保留 `feature_week_id` 方便审计，月份归属仍按 `target_date`。

**检查清单**：
- [ ] `CURRENT_STATUS.md` 写明 source benchmark 的 `confidence` 来源或代理规则。
- [ ] original/current benchmark 两侧使用同一 `confidence` 映射。
- [ ] 对外解释 CompareGate 时同时报告 direction match 和 confidence diff，且说明浮点容差。
- [ ] 不把 `confidence` 差异当成月度准确率或前端展示月份的依据。

## 坑 15：周频原始 batch 回测被误改成逐周 PIT，导致样本覆盖与 benchmark 不一致

**现象**（实际发生）：`weekly_10y_d_overlay_0529` latest backtest run 只从 2025-07 之后开始，前端“10Y国债活跃 · 周度”历史月度结果缺少 2025 年上半年。随后复查 `weekly_5y_direct_0529` / `weekly_7y_cross_d_overlay_0529`，也发现严格 PIT 重建后的 latest run 与原始 benchmark 样本覆盖不一致，导致同为周度、同为 2025-01-01 输出起点、同为 2026-06-01 灰度起点的方案，总样本数仍不一致。直接检查输入 weekly artifact 时，2025H1 周数据存在；问题不在前端隐藏，也不是 DB 缺数据。

**修复**：
1. `weekly_5y_direct_0529`、`weekly_7y_cross_d_overlay_0529`、`weekly_10y_d_overlay_0529` 历史回测作为批准例外，使用 source-original batch reproduction：全历史 weekly artifact 只传给 core 一次，再按 `feature_week_id` 映射平台 row。

3. 回测仍按灰度实盘边界过滤：`target_date < 2026-06-01`。
4. 落库前必须和已有 `original_predictions_sample.csv` 覆盖区间逐行一致；方向、target_date、label/is_correct 零差异，confidence 只允许 `1e-12` 以内浮点误差。
5. 实盘/灰度 adapter 不享受该例外，仍必须用 `end_week=feature_week_id`、`as_of_date=feature_date` 的严格 T+1/T 语义。

**2026-06-14 补充：重建为 source-original batch 后，样本数仍可能不同。** 三个周频方案的窗口和截断边界已经一致，但平台写入的是 core 实际发出的有效信号，不是所有日历周占位。当前 latest：5Y run_id=`109` 共 71 条，缺 `202534`；7Y run_id=`110` 共 68 条，缺 `202529/202534/202547/202608`；10Y run_id=`108` 共 72 条，无缺周。5Y 的 `202534` 是 `five_year_1y_momentum_4w` 原始信号为 0，`np.sign(0)=0` 后被规则投票排除；7Y 的缺周来自 7Y 主规则信号为 0 或 5Y 辅助信号缺失后被 `inner join` 排除。结论：这是算法输出本身，不是前端、DB、latest view 或回测窗口错误。除非业务明确批准改变算法语义，否则不得补写 flat/no-prediction 行来凑齐样本数。

**检查清单**：

- [ ] latest 5Y/7Y/10Y backtest summary 标记 `backtest_point_in_time=false`。
- [ ] benchmark 覆盖区间逐行一致校验通过后才允许 persist。

## 坑 21：把原始 benchmark 的 T 错对到平台 live `predict_date`

**严重等级**：Critical。这个错位会让原本正确的灰度/实盘样本看起来“缺行”或“错一天”，也会诱导后续修复把正确的 `feature_date` 改坏。

**现象**：原始算法 benchmark 里一条样本站在 `T=2026-05-29` 预测 `target_date=2026-06-05`。进入平台灰度/实盘后，正确记录应是：

```text
predict_date = 2026-06-01
feature_date = 2026-05-29
target_date  = 2026-06-05
```

如果用 benchmark 的 `T=2026-05-29` 去查数据库 `predict_date`，就会误判这条样本不存在；正确做法是用 benchmark 的 T 去查 `feature_date`。

**根因**：
1. 原始算法回测通常把“站在 T 预测”也叫 `predict_date` 或 `date`。
2. 平台语义中 `predict_date` 已固定为信号发出日 / 调度运行日。
3. 历史回测里 `predict_date=feature_date=T`，所以旧对齐方式短期看不出问题；一到灰度/实盘，`predict_date=T+1`，错位立刻暴露。

**强制规则**：
1. 原始 benchmark 的 `T/date/predict_date` 统一解释为 source T，即平台 `feature_date`。
2. benchmark 与最终 DB 明细核验必须按 `feature_date + target_date + target_tenor + horizon` 对齐；周频额外按 `feature_week_id` 对齐。
3. `predict_date` 只用于校验发出时点：回测 `predict_date=feature_date`，灰度/正式实盘 `predict_date` 是站在 `feature_date` 后按调度规则应发出的日期。
4. 若 benchmark 的 `target_date` 已进入灰度/实盘观察区，必须与 `t_scheme_predictions.feature_date` 对齐核验；若仍在历史回测区间，则与 `t_backtest_predictions.feature_date` 对齐核验。

**检查清单**：

## 坑 23：把 legacy core 的 `current_date` 误读成平台 `predict_date`

**严重等级**：High。这个问题会让回测边界少一天，尤其是 T1 这类 horizon 很短的方案，最后一个 target 日会被静默漏掉。

**现象**（实际发生）：`t1_daily` 旧 core 参数名叫 `current_date`，回测 runner 曾把结束边界写到 `2026-05-28`。结果 2026-05 最后一条 T1 target 只到 `2026-05-28`，缺少应有的 `target_date=2026-05-29`。

**根因**：
1. `current_date` 不是平台字段，也不是信号发出日。
2. 该 core 内部逻辑实际把它当成“目标验证日”，再选择最后一个 `< current_date` 的交易日作为模型站位。
3. 因此，若要生成最后一条 `target_date=2026-05-29` 的 T1 回测，必须传入 `target_date=2026-05-29`，得到 `feature_date=2026-05-28`；传入 `2026-05-28` 只会生成 `feature_date=2026-05-27 -> target_date=2026-05-28`。

**修复规则**：
1. `schemes/t1_daily/core/lgbm_predictor.py` 中旧 `current_date` 参数已重命名为 `target_date`，不保留兼容 alias。
2. `schemes/t1_daily/predict.py` 中 live 口径显式传 `target_date=predict_date`；对 T1 live 而言，信号发出日刚好等于目标验证日，但这是由 `feature_date=T, target_date=T+1, predict_date=T+1` 推导出来的，不是旧参数名。
3. `backtests/daily_0529_reproduction.py` 中 T1 回测结束边界为 `T1_BACKTEST_END = "2026-05-29"`，输出行仍满足历史回测 `predict_date=feature_date`。
4. 新增或改造 legacy core 时，必须先检查参数内部用法；任何含糊参数都要改成平台标准字段名，不能通过兼容 fallback 吞掉歧义。

**检查清单**：
- [ ] `rg current_date schemes/{scheme_id}/core schemes/{scheme_id}/predict.py backtests tests docs` 没有未解释的旧参数残留。
- [ ] 逐方案 benchmark 与 DB 明细用 `feature_date + target_date + target_tenor + horizon` 对齐，T1 最后一条 5 月样本为 `feature_date=2026-05-28,target_date=2026-05-29`。
- [ ] 同一前端任务格子 / 同一 `task_type` 列做样本覆盖对齐；若样本总数不一致，必须输出 `target_date` missing/extra 清单或已批准的算法有效信号例外。

## 坑 24：用假部署日或 `predict_date` 兜缺失 `target_date`

**严重等级**：High。这个问题不会让接口立刻报错，但会让前端显示一个看似合理的假日期，或者把回测样本归到错误月份，后续排查会被“正常展示”误导。

**现象**（实际发生）：
1. 前端在 registry/API 缺 `deployed_at` 时默认显示 `2026/06/01`，导致周度方案部署时间看起来被改成灰度起点。
2. 回测月度聚合曾在 `target_date` 缺失时退回 `predict_date`，旧数据缺字段时仍能生成月度行，掩盖了明细不完整。

**根因**：
1. 部署时间、灰度起点、正式实盘起点是三个不同概念。部署时间只能来自 `t_scheme_registry.deployed_at`，不能从其他日期猜。
2. `target_date` 是展示、去重、actual join 和月度归属的唯一事实字段；`predict_date` 只是信号发出日。
3. 兜底显示虽然能让页面“不空”，但会把数据注册问题变成业务语义错误。

**修复规则**：
1. active `t_scheme_registry` 行缺 `deployed_at` 时，`/api/schemes`、`/api/backtests/factor-lab` 和前端真实数据路径必须 fail-closed。
2. 前端不得保留 `DEFAULT_SCHEME_DEPLOYMENT_DATE`、scheme_id override 或用灰度/正式实盘起点替代部署时间。
3. `t_backtest_predictions.target_date` 缺失时，runner、API 和前端月度聚合必须 fail-closed；不得用 `predict_date`、`feature_date`、月份字段或旧月度汇总表回填。
4. mock/demo 数据如需展示部署时间，也要显式写入日期，不能复用生产兜底。

**检查清单**：
- [ ] `rg "DEFAULT_SCHEME_DEPLOYMENT_DATE" frontend tests` 无结果。
- [ ] `rg 'row\\.get\\("target_date"\\) or row\\.get\\("predict_date"\\)|target_date.*\\|\\|.*predict_date' backend backtests frontend` 无结果。
- [ ] `SELECT scheme_id FROM t_scheme_registry WHERE status='active' AND deployed_at IS NULL;` 无返回。
- [ ] 后端和前端测试覆盖缺 `deployed_at`、缺 backtest `target_date` 的 fail-closed 行为。
