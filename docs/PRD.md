# PRD: Bond Factor Lab 实盘测试系统

**版本**: v1.0  
**日期**: 2026-05-29  
**状态**: 需求确认完成

---

## 1. 背景与目标

### 1.1 背景

团队有多个国债收益率方向预测模型（基于LightGBM），需要在真实市场环境中持续验证各方案的预测表现。当前代码分散在不同目录，没有统一的管理和展示系统。

### 1.2 核心目标

在Mac Studio测试机上建立一个自动化的实盘测试平台：
- 每日开盘前自动运行所有活跃方案的预测
- 统一存储预测结果
- 前端实时展示各方案的准确率指标（按月、按期限维度）
- 支持方案的灵活增删

### 1.3 非目标

- 不涉及真实交易下单
- 不涉及真实交易策略回测；本项目只保留模型预测历史复现，用于校验方案迁移和前端展示口径
- 不替代panda_quantflow的其他功能

---

## 2. 用户与场景

### 2.1 用户

量化研究员（1-2人），需要：
- 每天查看各方案的最新预测
- 按月度/期限维度对比方案表现
- 快速判断哪个方案值得继续优化或上线

### 2.2 核心场景

1. **每日预测**: 工作日9:25自动运行所有方案，预测当日/未来N日的国债方向
2. **查看准确率**: 打开前端页面，选择方案/期限/时间范围，查看月度准确率矩阵
3. **新增方案**: 研究员开发了新模型，放入指定目录，系统自动识别并开始跟踪
4. **方案对比**: 同一期限下，对比不同方案的准确率表现

## 3. 功能需求

### 3.1 方案管理

| 需求 | 说明 |
|------|------|
| 方案注册 | 约定式目录结构，放入`schemes/`目录即自动发现 |
| 方案配置 | 每个方案一个config.yaml，定义元数据和调度规则 |
| 方案状态 | active/paused/archived三种状态 |
| 方案增删 | 新增：创建目录+config.yaml+predict.py；删除：归档或移除目录 |

### 3.2 预测调度

| 需求 | 说明 |
|------|------|
| 定时执行 | 工作日9:25自动运行（可按方案配置） |
| 交易日判断 | 跳过非交易日（周末+法定假日） |
| 执行隔离 | 各方案独立执行，一个失败不影响其他 |
| 运行日志 | 记录每次执行的状态、耗时、错误信息 |
| 手动触发 | 支持通过API手动触发某个方案运行 |

### 3.3 数据存储

| 需求 | 说明 |
|------|------|
| 预测结果 | 统一写入MySQL，字段：scheme_id, tenor, horizon, predict_date, target_date, direction, confidence |
| 实际方向 | 每日收盘后更新实际收益率方向（T+1和T+5） |
| 数据隔离 | `scheme_id` 是方案实例唯一身份；`tenor + horizon` 是任务格子，同一任务格子下允许多个 `scheme_id` 并存 |
| 标的注册 | `t_target_registry` 管理内部 key 与展示名，例如 `3Y -> 3Y国债活跃`，支持后续扩展其他品种 Y |
| 幂等写入 | 同一天重跑不会产生重复数据（UPSERT语义） |

### 3.4 前端展示

| 需求 | 说明 |
|------|------|
| 任务矩阵 | 按 `Y标的 × 预测长度` 形成任务格子，例如 `5Y国债活跃 + T+1` |
| 方案排行 | 点击任务格子后，展示该格子下所有候选方案的排行 |
| 标的筛选 | 按 Y 标的筛选（当前展示 `3Y国债活跃/5Y国债活跃/7Y国债活跃/10Y国债活跃`；当前不展示1Y预测目标） |
| 时间范围 | 月份范围选择器 |
| 准确率矩阵 | 按月展示：整体准确率、上涨准确率/召回率、下跌准确率/召回率 |
| 指标汇总 | 选定范围内的综合指标卡片 |
| 趋势图 | 各指标的月度趋势折线图 |
| 每日明细 | 点击某月可展开查看每日预测vs实际 |
| 运行状态 | 显示方案最近一次运行的状态和时间 |

### 3.5 指标计算逻辑

对于选定的任务格子和方案实例，即 `target_tenor + horizon + scheme_id + 月份范围`：

```
predictions = SELECT * FROM t_scheme_predictions WHERE ...
actuals = SELECT * FROM t_scheme_actuals WHERE ...

对每个月:
  matched = JOIN predictions.target_date = actuals.trade_date
  total = count(matched)
  correct = count(predicted_direction == actual_direction)
  
  overall_accuracy = correct / total
  up_precision = TP_up / (TP_up + FP_up)
  up_recall = TP_up / (TP_up + FN_up)
  down_precision = TP_down / (TP_down + FP_down)
  down_recall = TP_down / (TP_down + FN_down)

跨月区间指标必须按样本级重新聚合: 先汇总区间内 TP、预测方向数、实际方向数、总样本数，再计算 accuracy/precision/recall；不得对各月百分比做简单平均。
```

## 4. 已确认的设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 部署位置 | 全部在Mac Studio | 简化架构，数据就近访问 |
| 实盘含义 | 每日预测+事后验证 | 不涉及真实交易 |
| 数据来源 | MySQL bond_db（已有服务自动更新） | 预测脚本只读取 |
| 预测存储 | 统一MySQL表 | 方便跨方案查询和对比 |
| 调度方式 | APScheduler（Python进程） | 配合config.yaml，新增方案无需改crontab |
| 前端框架 | 原生HTML/CSS/JS（从panda_quantflow提取） | 已有完整实现，无需引入构建工具，后续只需替换mock为API调用 |
| 方案发现 | 约定式目录结构 | 新增方案零代码改动 |
| 与panda_quantflow关系 | 独立项目，iframe嵌入 | 解耦，独立迭代 |
| 验证方式 | 后端实时计算 | 保证计算一致性，前端轻量 |
| 运行时间 | 工作日9:25 | 开盘前，数据已更新 |
| 方案规模 | 5-10个 | 短期目标 |

## 5. 当前方案清单

### 方案1: t1_daily (0529原始T1-LGBM滚动基准)

- **来源**: 0529 t1 算法，已框架化到 `schemes/t1_daily/`
- **展示名**: `0529原始T1-LGBM滚动基准`
- **期限**: 5Y, 10Y
- **预测跨度**: T+1（预测明天的方向）
- **模型**: LightGBM二分类，滚动训练窗口126天
- **特征**: 基于Wind指标的宽表（877列）
- **投票**: 硬编码信号增强
- **标签**: `close.shift(-1) / close - 1` 的方向

### 方案2: t5_daily (0529原始T5-LGBM投票基准)

- **来源**: 0529 t5 算法，已框架化到 `schemes/t5_daily/`
- **展示名**: `0529原始T5-LGBM投票基准`
- **期限**: 3Y, 5Y, 7Y, 10Y
- **预测跨度**: T+5（预测5个交易日后的方向）
- **模型**: LightGBM二分类，各tenor独立参数
- **特征**: 同上宽表 + tenor特定的z-score/anti-lag/momentum信号
- **投票**: 各tenor独立投票配方
- **GAP**: 排除最近5天样本避免标签重叠

## 6. 约束与风险

| 约束/风险 | 应对 |
|-----------|------|
| 数据库密码硬编码 | 迁移到环境变量 |
| t1和t5逻辑差异大 | 各自独立adapter，不强行统一内部逻辑 |
| 非交易日判断 | 使用chinese-calendar库 |
| 模型训练耗时 | 9:25开始，需确保9:30前完成 |
| Mac Studio重启后恢复 | launchd KeepAlive确保自动重启 |
